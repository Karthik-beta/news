# ADR 0004: DynamoDB single table, search shards and storage split

- Status: accepted (Phase 6, issue #6)
- Date: 15 November 2026
- Contracts: `contracts/cloud/dynamodb-items.schema.json`, `contracts/bundle/meta.schema.json`

## Context

DynamoDB is the cloud's database of record. The free tier gives 25 read and 25 write capacity units, shared by every table and index in the account, and caps items at 400 KB. A write unit is 1 KB per second, so item size, not item count, sets publishing speed. The Technical Design (TD, "DynamoDB") fixed a single table with `PAGE#`, `HUB#`, `ENT#`, `TAX#`, `URL#` and `HOME#CURATION` keys. The write API also needs idempotency records and a way to keep two operations on one page apart.

## Decision

One table, string keys `PK` and `SK`, no secondary index. Item shapes are in the items schema; every content record carries `lang` (bookkeeping items, idempotency records and page locks, do not).

| Item | PK | SK | Notes |
| --- | --- | --- | --- |
| Page version | `PAGE#<page_id>` | `V#<000001>` | Written once per version, never changed |
| Live page | `PAGE#<page_id>` | `LATEST` | Moved last on publish: the commit point readers see |
| Page lock | `PAGE#<page_id>` | `LOCK` | One write operation per page at a time; 2-minute lease; bookkeeping, no `lang` |
| Path claim | `URL#<page path>` | `PAGE` | One page per URL and R2 prefix; lookup by path |
| Hub entry | `HUB#<hub>` | `<first published_at>#<page_id>` | Hubs: `latest`, `cat/<slug>` (and each parent), `ent/<entity id>`, `region/<region>` |
| Entity | `ENT#<entity id>` | `META` | Its pages are hub `ent/<entity id>` |
| Taxonomy node | `TAX#tree` | `NODE#<slug>` | Changed from the TD's `TAX#<id>` / `META` (below) |
| Redirect | `URL#<old path>` | `REDIRECT` | |
| Curation | `HOME#CURATION` | `V#<000001>` and `LATEST` | ADR 0005 |
| Idempotency | `IDEM#<SHA-256 of key>` | `META` | Bookkeeping, no `lang`; TTL 7 days |
| Operation result | `IDEM#<SHA-256 of key>` | `RESULT` | What a committed curation published, written in its commit transaction (ADR 0005); TTL 7 days |

- **Versions are zero-padded** (`V#000010`), because sort keys compare as strings and `V#10` would sort before `V#2`. "Newest version" is one `Query` with `ScanIndexForward=false, Limit=1`.
- **Hub entries keep the first publication time** in their sort key, so an update does not move a page to the top of its hubs. Each entry copies the listing fields (title, summary, type, tier, region, dates, index status), so a hub renders from one `Query`. The live page record lists its hubs, so an update deletes the entries of hubs the page left and a withdrawal deletes them all.
- **Taxonomy is one partition.** The TD put each node under its own key; then listing the tree needs a scan or an index. `TAX#tree` / `NODE#<slug>` keeps per-node reads and makes the whole tree one `Query`.
- **Items stay small: metadata only.** Every bundle file, including `page.oui`, lives in R2 under the page's path (`2026/11/<slug>/index.html`, `index.md`, `data.json`, `sources.json`, `meta.json`, `page.oui`, `charts/<id>.csv`). This changes the TD's "items hold metadata, .oui, summary": a 30 KB `.oui` would cost 30 write units on every version and every update. A page record is 2–4 KB and the API refuses one over 64 KB.
- **No secondary index.** Every read path is a key lookup or a single-partition query. The one index the free tier can afford is kept for a later need (for example pages by index status, if sitemaps outgrow the hub listings).
- **Paced writes.** A write unit is 1 KB, per item, rounded up; a transactional write costs twice. A typical publish (a 3 KB page record, 6–10 hubs, 1–3 entities) writes: page lock 2, idempotency 2–3, path claim 1, version record 3, `LATEST` about 8 (a transaction: twice its 3 KB plus the lock check), hub entries 2 each (12–20), new or changed entities 1 each: **about 35 write units**, over a second of the free table's 25 per second. The schema's worst case is far larger: 8 categories with 4 levels each plus 50 entities is 84 hubs (about 170 units, and as many again to delete them when a page leaves them), 50 entities, and a page record of up to 64 KB (2,000 data IDs) written as the version record and transactionally as `LATEST`: **600–700 units, about 25 seconds of capacity**. So the safe pace is **at most one page per second, and fewer when pages are large**; DynamoDB's burst capacity (300 seconds of unused units) absorbs short runs. The Bureau Design's Press pace (3.12) says the same. Entities the live version already lists with the same name and kind are not rewritten. The Worker does not retry a throttled write: it releases the idempotency key and answers 503 `throttled` with `Retry-After`, and the laptop retries with the same key. R2 file writes run at most 6 at a time.
- **Subrequests.** The Workers free plan allows 50 external subrequests per request, and every DynamoDB call and purge call is one (R2 and D1 bindings count against Cloudflare's separate limit for its own services). So hub entries, entities and hub deletions go 25 to a `BatchWriteItem` call (unprocessed items retried twice, then 503 `throttled`), and purges 30 URLs to a call. A publish counts its calls before writing anything (12 single calls, the batches and the purge calls) and is refused (400 `invalid_meta`, detail `meta.too_many_writes`) above 45, which leaves room for retries. At the schema's maximum (84 hubs, 50 entities, 64 files, every hub replaced) a publish makes about 32 and a withdrawal about 18; `recovery.test.ts` counts them. Over the limit, `fetch` fails before sending, so that failure is an ordinary error (lock and key released), not an unknown outcome.
- **One writer per page.** Publish, withdraw and index promotion take the page lock (`PAGE#<id>` / `LOCK`, a create-only put with a random owner; one older than 2 minutes is stale and may be taken over) before they read the page, and give it back when done; a second operation meanwhile gets 409 `page_busy`. Page files are served by the CDN straight from R2 at the page's public path, so they are rewritten in place; versioned R2 keys would not remove the need to serialise the writers of that public copy, and would double storage against the 10 GB free tier. Each file is stamped with its version (R2 custom metadata), so a reader (the MCP server) can tell a file written ahead of `LATEST` and re-read the record instead of mislabelling it. Because a lock can be taken over, a holder must not write after its lease; the operation is fenced (`workers/api/src/lock.ts`):
  - **Deadline.** No page write starts more than 100 seconds after the lock was taken (20 seconds before it can go stale). The check runs before every step, every R2 file, every batch and the purge; past it the operation stops, gives back its lock and key and answers 503 `lock_expired`, and the retry finishes the job.
  - **Bounded calls.** Every storage call has a timeout: DynamoDB 8 seconds (its client), R2 and D1 10 seconds. So every call started before the deadline is answered or abandoned before the lease ends. An abandoned call may still be applied, so it is an unknown outcome: the key and lock are kept until stale (503 `outcome_unknown`), never given back early. A failed write among parallel ones waits for the others to finish before anything is released.
  - **Fenced commit.** Moving `LATEST`, the withdraw and index status changes and clearing the cleanup note are transactions with a `ConditionCheck` that `LOCK.owner` is still this request. A holder that lost its lock can never change the live record; it answers 503 `lock_expired` and leaves the new holder's lock alone.
  - **The guarantee**, precisely: while clocks agree within a few seconds, a request that took the lock at time T issues no page write after T + 100 s, and every write it issued is answered or abandoned by T + 110 s, before anyone can take over at T + 120 s. The live record (`LATEST`) is never changed by a request that no longer holds the lock. What is not fenced is a write the storage service accepted but held for more than about 10 seconds past its own timeout: R2 and DynamoDB offer no condition on another item for unconditional puts, and re-reading the lock before each batch would cost a subrequest each and still leave the same gap between read and write. Such a late write could only touch files and hub entries of the page, which carry or match the version they belong to; the next publish rewrites them. Re-checking the lock per batch was not chosen for that reason.
- **Write order.** Body checks (no lock, no writes), page lock, reads and conflict checks (an older version, a reused version number with other content, a URL change, the version of a withdrawn page: refused before any write), the subrequest plan, path claim, version record (`attribute_not_exists OR same bundle_sha256`), R2 files, hub entries and entities, search row, then `LATEST` (`attribute_not_exists OR version <= n`, with the lock check) carrying a `cleanup` note of the hubs and files the previous version had and this one dropped; then those hub entries and files are removed, the purge runs, and the note is cleared. The version record comes first because it lists every hub and file the publish may write: if the publish never commits, its record stays above `LATEST`, and the next publish (or a withdrawal) reads the version records above `LATEST`, adds what they list and the new state does not keep to its cleanup, and purges it. A first publication that never committed also fixes the page's URL and publication time for the next attempt, so hub sort keys and the search shard stay the same. Every step is idempotent and the note is part of the commit, so a retry after a failure anywhere (or the next version) finishes the job, including the purge of the hubs and files the page left. Withdraw and index promotion re-run all their steps on every attempt. A curation's commit transaction also records its version under the request's key (`IDEM#<hash>` / `RESULT`, ADR 0005), so a retry finds the version it already wrote, before validating the draft again, instead of publishing another. A write that got no answer (timeout, 5xx) may have been applied: the Worker keeps the idempotency key and page lock until they go stale and answers 503 `outcome_unknown`. Transactions are used for the curation and redirects (ADR 0005) and for the fenced page commits above.
- **Read consistency.** The write API reads strongly (it reads what it just wrote). Public readers (the MCP server, the site) read eventually consistently, which costs half the read units and lags by about a second.
- **Timestamps** are stored in one form, `Date.toISOString()` (three fractional digits), so they compare and sort as times; days that do not exist are refused.

**Reports are not in this table.** Reader reports live in their own D1 database (ADR 0006), so report traffic can never spend the write units publishing needs.

**Search (D1).** One D1 database per publication year, bound as `SEARCH_<YYYY>` (each free database holds 500 MB). The schema is `workers/shared/migrations/search/0001_pages.sql`: a `pages` table and an external-content FTS5 table over title, summary, entities, tags and categories (with parents), kept in sync by triggers (the update trigger fires only when an indexed column changes, so an index-status change is one row write). Queries become quoted words only, so no FTS5 syntax from a reader reaches the database. Shards are searched newest first until the limit is met. A page lives in the shard of its first publication year; the API refuses a page whose year has no shard bound, before writing anything.

**Index status.** `index_status` is stored on the page record, its hub entries and its search row. `POST /v1/pages/{id}/index` changes all three and purges the page's URLs. `meta.json`'s `index_status` applies only to a page's first publication; a new version keeps the live value, so a republish never undoes a promotion (Edition step 11 owns the status after that). The robots meta and sitemap entry must follow `index_status` at serving time (an open item for the site and sitemap work, #14).

## Consequences

- Adding a hub kind, an entity or a category needs no schema change.
- A typical publish costs about a second and a half of the table's write capacity and a worst-case one about 25 seconds; the publish rate is set on the laptop (at most one page a second).
- Items are validated in tests against the items schema, so a change to an item shape must change the contract first.
- For the docs owner (#9): the TD's DynamoDB table should gain the path claim, `IDEM#` and page-lock rows, the `TAX#tree` change, "files in R2, not in items" and "reports in D1, not in DynamoDB". The Press (#20) must also check a bundle's total body size against the API's 1 MiB cap: the manifest allows files of up to 1 MiB each.
