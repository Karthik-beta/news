# ADR 0006: Security of the write API, report intake and MCP server

- Status: accepted (Phase 6, issue #6)
- Date: 15 November 2026
- Contracts: `contracts/cloud/write-api.openapi.json`, `report.schema.json`, `mcp-tools.schema.json`

## Context

The write API changes everything readers see; the report intake and the MCP server take input from anyone. All three run on the Workers free plan (little CPU per request, a daily request quota) and must not run AI (TD principle 3).

## Decision

**One secret key.** Every write API route except `/health` and the report intake needs `Authorization: Bearer <NEWS_WRITE_API_KEY>`. The key lives only in the laptop's `.env` and as a Worker secret, is at least 32 characters, and is rotated by setting a new secret and a new `.env` value. Comparison hashes both sides with SHA-256 and compares the 32-byte digests with a constant-time loop, so neither the key's length nor the position of a mismatch leaks. With no key (or a short one) configured, every write is refused (fail closed). Everything under `/v1/` except the report intake is authenticated before any other check, including routing and the method check, so an unauthenticated caller learns nothing about which paths exist. Failed attempts are rate-limited per client IP (10 a minute, per Cloudflare location); a client that hits the limit is refused before any key comparison until its minute is up (remembered per isolate), so even a right guess gets nothing. Keys, bodies, e-mails and IPs are never logged, and the Workers' invocation logs (which record request metadata such as the client IP) are turned off.

**Idempotency.** Every write needs an `Idempotency-Key` (Stripe-style; the publisher sends `<page_id>:<version>:<bundle_sha256>`). The API first reads `IDEM#<SHA-256 of key>`: a finished record with the same request hash (method, path, exact body) is replayed byte for byte with `Idempotent-Replayed: true` and nothing is written; a different hash is 409 `idempotency_key_reused`; a pending record younger than 2 minutes is 409 `idempotency_in_progress`. Otherwise the request is validated, a pending record is created with a create-only put, the operation runs, and the record becomes `done` with the response. A failure releases the record so the retry runs again, and every operation finishes on a retry what a failed attempt left undone (ADR 0004). A database write that got no answer may have been applied, so it is not released: the key (and the page lock) stay held until stale, and the answer is 503 `outcome_unknown` with `Retry-After: 120`. Records expire after 7 days (DynamoDB TTL on `expires_at`).

**Schema validation everywhere.** Every body is checked by validators compiled ahead of time from `contracts/` (`workers/shared/src/generated/validators.js`): workerd forbids runtime code generation and a free-plan request has little CPU. A unit test fails when the generated file is out of date. Schemas use closed objects (`additionalProperties: false`), anchored patterns without nested ambiguous quantifiers, and length limits. Error details carry JSON Pointers, never the offending values. Bodies are read with a hard cap enforced from `Content-Length` and again while streaming (pages 1 MiB, curation 64 KiB, small operations 4 KiB, reports 8 KiB, MCP 64 KiB). The page cap is measured: JSON.parse and SHA-256 of every file cost about 8 ms of CPU per MiB against the free plan's 10 ms, and real bundles are 100–300 KB. Bundle files are checked against their manifest hashes and sizes, the bundle hash is recomputed, file names come from a fixed list, and content types are set by the server.

**Least privilege.** The api Worker's DynamoDB key may only read and write items of the one table (`GetItem`, `BatchGetItem`, `Query`, `PutItem`, `DeleteItem`, `ConditionCheckItem`): no `Scan`, `UpdateItem`, `UpdateTable`, `DeleteTable` or other table management. The MCP Worker gets a separate read-only key (`GetItem`, `BatchGetItem`, `Query`) whose `dynamodb:LeadingKeys` are limited to the public partitions (`PAGE#`, `HUB#`, `ENT#`, `TAX#tree`, `URL#`), so it cannot read idempotency records; it only reads R2 and only runs `SELECT`s on D1. Both IAM policies are written out in `workers/README.md`. The purge token has only Zone > Cache Purge on the site's zone. The DynamoDB client refuses any endpoint except the region's official HTTPS endpoint or loopback (DynamoDB Local), so a bad setting cannot send signed requests elsewhere.

**Rate limits within the free plan.** Workers Rate Limiting bindings (`ratelimits` in `wrangler.jsonc`; free, no account setup): failed write-key attempts 10/min per IP; report intake 5/min per IP and 60/min per location; MCP 30/min per IP. These limits are **per Cloudflare location and approximate**, not global: a sender spread over many locations multiplies them. The one global limit is the report intake's daily cap, which the reports database enforces (below).

**Keeping public traffic off the publishing table.** DynamoDB's 25 read and 25 write units per second are shared by publishing, the site and the MCP server. The report intake never touches the table (reports and the page check live in D1). The MCP server reads eventually consistently (half the read units), answers repeated identical calls from the edge cache (60 seconds, 5 minutes for the category tree, "not found" included), lists at most 20 pages per entity, refuses searches of more than 8 words and searches a last word as a prefix only from 3 characters. A real global budget for MCP (a cap on table reads across all locations) needs either a WAF rate-limiting rule on `/mcp` or a Durable Object counter. A Durable Object on every MCP call would double the request count against the free daily quota and add a round trip to one location, and a daily cap would not protect a per-second read budget, so it is not built in: **a WAF rate-limiting rule on `/mcp` is a deployment step for #21** (the free plan includes one rule), to revisit with a Durable Object if MCP traffic grows. Heavy MCP users are pointed at the bulk dumps.

**Report intake spam controls.** Size limit 8 KiB, text at most 2,000 characters and 4,000 bytes, an optional `where` ("Where on the page?", 200 characters); JSON only; the per-IP and per-location limits; a hidden `website` honeypot (filled: answered 202 as if accepted, nothing stored); the page must be published (checked in the search index); requests from another site's Origin are refused (403) and CORS allows only the site. Reports are stored in their own D1 database (binding `REPORTS`), never in the DynamoDB table, so a flood cannot spend publishing's write units. A **global daily cap** (`NEWS_REPORT_DAILY_CAP`, default 200) is enforced by the database itself: one `INSERT … SELECT … WHERE` the day's count is under the cap, so concurrent reports cannot exceed it; once an isolate sees the cap reached it refuses without a query until the UTC day ends. The stored row is the report text, kind, page, optional where and e-mail, language and receipt time; never the IP address, user agent or other request details. The IP is only the rate limiter's in-memory key. Rows expire after 180 days (the pull skips and deletes expired ones); `news corrections pull` (Errata) reads them with the write key. **Report text is untrusted input**: Errata and its triage call (A9) treat `text` and `where` as data only (fenced, never instructions, in a model call with no tools), and no correction is published without Karthik's approval. Turnstile was considered and left out for now: it needs a widget on the site's form (#14), and the daily cap already bounds the damage. The e-mail is stored in the cloud only so Karthik can reply; the Errata workflow keeps it out of the local store (Bureau Design 9.3).

**MCP server.** Stateless and read-only, MCP specification revision 2026-07-28 over Streamable HTTP at `POST /mcp`: no sessions (an `Mcp-Session-Id` is ignored and never minted), GET and DELETE are 405, each request carries its protocol version in `_meta` and the `MCP-Protocol-Version` header, `Mcp-Method` and `Mcp-Name` must match the body (400 `HeaderMismatch`). For older clients the server is dual-era: it answers `initialize` for 2025-11-25 and 2025-06-18 without creating a session. Browser Origins other than the site (and `NEWS_MCP_ALLOWED_ORIGINS`) are refused (403, DNS-rebinding defence); an allowed one gets its CORS preflight answered and CORS headers on every response. Tools validate their arguments with the same precompiled validators; invalid arguments are tool errors the model can correct. Content returned by one call is capped (Markdown 60 KB, data 100 KB, the whole JSON-RPC response 512 KB) with truncation flagged and a link to the full file; figures are returned exactly as published, and a file is never labelled with another version than its own (ADR 0004).

**No AI in the cloud.** No Worker may import a model SDK or bind Workers AI. `workers/shared/src/ai-guard.test.ts` scans every Worker's sources, `package.json` and `wrangler.jsonc` and fails on any of them.

## Consequences

- A leaked write key allows writes until rotated; there is one key by design (TD Security). Rotation is a secret update plus a `.env` change.
- The per-minute rate limits are per location; a distributed sender can exceed them, but not the reports' daily cap, and it cannot touch the publishing table through the report intake. MCP has no global budget until the WAF rule is in place (#21).
- The MCP server's dual-era support can be dropped once clients have moved to 2026-07-28.
